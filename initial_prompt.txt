# Project Prompt: Build "MockApp" — Standalone Offline Bootstrap UI Mockup Designer
You are acting as the lead software architect, UX designer, and senior implementation engineer for a new application called **MockApp**.

MockApp is a standalone desktop-browser web application for visually designing realistic Bootstrap-based UI mockups.

The application should feel conceptually similar to draw.io / diagrams.net in its interaction model:

- component palette on the left
- large central design canvas
- property inspector on the right
- toolbar/menu at the top
- drag and drop
- selection
- resizing
- alignment
- zooming
- keyboard shortcuts
- open/save/export workflows

However, MockApp is specifically intended for designing realistic Bootstrap user interfaces rather than diagrams.

The project must prioritize:

1. maintainability
2. modularity
3. clean separation of responsibilities
4. offline operation
5. no server requirement
6. clear internal documentation
7. AI-maintainability
8. future Bootstrap upgrades
9. future feature expansion
10. predictable project file organization

Do NOT immediately start implementing the application.

Follow the mandatory workflow defined below.

---

# 1. PRIMARY PRODUCT GOAL
Create a visual Bootstrap UI mockup designer called **MockApp**.

The user must be able to launch it locally by opening:

`mockapp.html`

directly in a modern browser.

No web server must be required.

The application must work offline after the repository/package has been downloaded.

There must be no required CDN calls or remote runtime dependencies.

All runtime libraries, fonts, icons, Bootstrap assets, JavaScript libraries, CSS libraries, and other required resources must be stored locally inside the project.

The application may contain many supporting files.

In fact, modularity is preferred over embedding everything into `mockapp.html`.

`mockapp.html` should remain as small and simple as reasonably possible.

Do NOT create a giant monolithic HTML file unless there is a compelling technical reason.

---

# 2. IMPORTANT ARCHITECTURAL PRINCIPLE
The goal is NOT to create a single-file application.

The goal is:

- one obvious entry point: `mockapp.html`
- many well-organized supporting files
- clean modules
- locally stored dependencies
- easy future maintenance
- easy Bootstrap upgrades
- easy AI-assisted code modification

Prefer multiple focused files over large files.

Examples:

- separate UI shell logic
- separate canvas logic
- separate drag/drop logic
- separate selection logic
- separate resize logic
- separate keyboard logic
- separate project persistence logic
- separate export logic
- separate Bootstrap component definitions
- separate property editors
- separate utilities

Avoid unnecessarily large source files.

As a general guideline:

- keep modules focused on one responsibility
- split files that become difficult to understand
- avoid files containing unrelated subsystems
- avoid files containing hundreds of unrelated functions

---

# 3. BOOTSTRAP REQUIREMENTS
Use the **latest stable Bootstrap release available at implementation time**.

Also include the corresponding/current **Bootstrap Icons** package.

Bootstrap and Bootstrap Icons must be stored locally.

Do not use CDN links in the final application.

Keep vendor code clearly separated from application code.

Recommended structure:

`vendor/bootstrap/...`

`vendor/bootstrap-icons/...`

Do not modify vendored Bootstrap source files unless absolutely necessary.

Application overrides should live in MockApp-specific stylesheets.

Bootstrap should be upgradeable in the future by replacing/updating vendor files with minimal impact on MockApp source code.

Document the exact installed Bootstrap version.

---

# 4. BROWSER SUPPORT
Target current desktop versions of:

- Google Chrome
- Microsoft Edge
- Mozilla Firefox
- Safari

Legacy browser support is not required.

The application should primarily target desktop/laptop use.

Tablet use may work but is not the primary interaction model.

# 9. FILE_INDEX.md — CRITICAL PROJECT MAP

- public responsibilities

```

Purpose:

Subsystem:
Canvas interaction.

Responsibilities:
- single selection
- multi-selection
- selection rectangle
- selection highlighting

Important exports:
- selectElement(id)

- toggleSelection(id)
- selectRange(rect)

- app-state.js

- changing selection rules

- changing click/shift-click behavior

Do NOT modify this file when:
- changing component property definitions
- changing project save format
```
Keep this document updated throughout implementation.

If a file is created or removed, update `FILE_INDEX.md` in the same change.
